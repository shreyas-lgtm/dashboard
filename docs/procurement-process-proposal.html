The short answer

Yes, and the trigger to use is column J — the one Google Sheets is currently labelling Column 9 because its header cell is empty. It holds Approved 57 times and Rejected 3 times across 78 requests: a 77% decision rate. That is a working approval gate.

Do not trigger on Final Approval (column K). It contains only Approved, 18 times, and all 18 are a subset of column J. It is a half-adopted second stamp and it should be retired, not automated.

Firing on column J gives roughly 19 tickets a week. The real remaining problem is not bypassed approvals — it is that 10 of 27 requests marked Critical — within 24 hours have no decision at all, and the undecided pool averages 11 days old.

Correction to the first draft of this document

An earlier version of this page reported that 36 requests had been procured with no approval recorded, and recommended fixing the approval gate before automating it. That was measured against Final Approval and was wrong. Measured against column J, the true figure is 2, and rejection demonstrably works — all three rejected requests were left at Pending and never ordered. The gate does not need fixing before automation. The sections below are corrected.

Approval works; the queue does not. With 60 of 78 requests carrying a decision and only two anomalies — PR-2026-1473 and PR-2026-1463, both handed over without a decision recorded — there is no systemic bypass to fix. What there is instead is an ageing undecided pile: 16 of the 18 blanks are still at Pending, median age 11 days, and 10 of them are self-declared 24-hour criticals.

This is the strongest argument for putting these in Asana. A spreadsheet row cannot chase anybody. A ticket with an assignee, a due date and an escalation rule can. The problem is not that approval is being skipped — it is that a request with nobody's name on it waits indefinitely, and the sheet gives no signal when it does.

Urgency has inflated because it is free. A third of all requests claim 24-hour criticality, self-declared on a dropdown with no need-by date behind it and no cost attached. Notably, every one of the 8 Planned requests got decided while 10 criticals did not — a reasonable sign the label is being discounted by the people reading it.

02 The structural problem: three systems, no boundaries

Before choosing an integration, it is worth naming why the sheet's tracking columns went dead. You currently have three systems that each believe they own a purchase request:

Current ownership overlap
SystemWhat it holds todayReality check
Google Form + Sheet Intake and approval — plus an aspirational fulfilment tail: order ID, delivery date, ETA, SCM remark Intake works (100% fill on requester, vendor, justification) and so does approval (77% in column J). The fulfilment tail is 0% filled.
Zoho Procurement The real ledger: PRs, POs, vendors, receipts, bills, spend Order ID is blank on all 78 rows, so nothing links a request to its PO. The two systems do not know about each other.
Asana Starter Nothing yet — 60 seats being rolled out via Addrs Labs Risk: becomes a third place to retype the same request unless its job is defined narrowly.

The sheet's tail is empty because it duplicates fields Zoho already owns natively. People correctly declined to type delivery dates twice. Any new process should assign one system of record per stage and let the others read from it — which is the principle the proposal below is built on.

05 How to sequence it

Phase 1 · ~2 days

Automate on column J, keep the Google Form

  • Name column J — give J1 a real header such as Approval Decision. It is only called Column 9 because the cell is blank.
  • Apps Script installable onEdit trigger watching column J: when it becomes Approved, create the Asana task. It must be onEdit, not onFormSubmit — approval is entered well after submission.
  • Write the task URL into a new column and skip rows that already have one, so re-editing J never mints a duplicate.
  • Rejected creates nothing, or a closed task for the record.
  • Retire Final Approval (column K) so there is exactly one approval field.
Phase 2 · after tiers are agreed

Move intake and approval into Asana

  • Native Asana form replaces the Google Form; tasks land in a Procurement project.
  • Approval happens on the ticket, so the timestamp is system-generated and the audit trail is real.
  • Sections mirror the stages; PR_ID, cost, team, category become custom fields.
  • The sheet becomes an archive, not a tracker.
Phase 3

Link Asana to Zoho and close the reporting gap

  • Approved ticket creates the Zoho PR/PO; PO number flows back to the ticket.
  • Dashboard gains front-half metrics: intake volume, approval cycle time, bypass count.
  • Order ID finally populates — automatically.

Phase 1 stands on its own and is worth doing this week: column J is already a reliable signal, so the tickets it produces will reflect real approved procurement from day one — about 19 a week at current volume. It does not fix the ageing undecided pile, because it only fires once a decision exists. Phase 2 is what addresses that, by putting the pending request itself on someone's board with a due date.
